# 第一部分：项目介绍（5 分钟）

## 1. 请简单介绍你的项目 ⭐必背

**答：** 我做的是一个 Linux 系统资源监控项目，用 C++11 写的。它从 Linux 的 `/proc` 文件系统采集 CPU、内存、网络、软中断等系统指标，通过 gRPC + Protocol Buffers 把数据发到服务端，再用 Python Web Dashboard 做可视化展示。整体是采集层 → 通信层 → 展示层的三层架构，代码量大概 2000 行，Docker 一键部署。

---

## 2. 项目解决了什么问题？

**答：** 运维需要知道服务器的实时状态——CPU 用了多少、内存剩多少、网络流量多大。Linux 虽然提供了 `/proc` 文件系统暴露这些信息，但都是原始文本或累计值，不直观也不方便直接使用。我这个项目把原始数据采集下来，做差分计算转成速率/百分比，通过 gRPC 传输汇总，然后在 Web 页面实时展示。

---

## 3. 项目的整体架构是怎样的？⭐必背

**答：** 四层架构。

- **数据采集层（`linux_monitor/`）**：5 个监控器，用策略模式，都继承 `MonitorInter` 接口
- **通信层（`rpc_manager/`）**：gRPC 客户端封发数据，服务端收数据并缓存
- **协议层（`proto/`）**：Protocol Buffers 定义数据格式和 RPC 接口
- **展示层（`web_dashboard/`）**：Python Flask Web 页面

---

## 4. 监控了哪些指标？怎么采集的？

| 指标 | 数据源 | 计算方式 |
|------|--------|----------|
| CPU 负载 | `/proc/loadavg` | 直接读取 |
| CPU 使用率 | `/proc/stat` | 差分计算（8 种状态百分比） |
| 内存 | `/proc/meminfo` | 直接读取（19 项指标，KB→GB） |
| 网络速率 | `/proc/net/dev` | 差分计算（收发 KB/s，包/s） |
| 软中断 | `/proc/softirqs` | 差分计算（10 类中断速率） |

---

## 5. 项目中你用到哪些设计模式？

**答：** 策略模式（监控器框架，`MonitorInter` 接口 + 5 个子类实现）、RAII（`ReadFile` 管理文件句柄，`lock_guard` 管理互斥锁）、工厂模式（通过基类指针统一管理不同类型的监控器对象）。

# 第二部分：操作系统八股（5 分钟）

## 6. 进程和线程的区别？⭐必背

**答：**

| 维度 | 进程 | 线程 |
|------|------|------|
| 资源 | 独立的内存空间、文件描述符表 | 共享进程的内存和资源 |
| 通信 | IPC（管道、消息队列、共享内存） | 直接读写共享变量 |
| 切换开销 | 大（切换页表、TLB 刷新） | 小（只切换寄存器和栈） |
| 创建开销 | 大（fork 复制页表） | 小 |
| 独立性 | 一个进程崩溃不影响其他进程 | 一个线程崩溃可能拖垮整个进程 |

**结合项目：** 本项目 `main.cpp` 中主线程创建了一个采集线程。采集线程用 lambda 捕获主线程的 `runners_`、`rpc_client_` 等变量，线程间通过共享变量通信。`main` 线程创建完采集线程后 `join()` 等待。

---

## 7. 线程同步有哪些方式？你项目里用了什么？⭐必背

**答：**

| 方式 | 原理 | 适用场景 |
|------|------|----------|
| 互斥锁 `std::mutex` | 同一时刻只有一个线程持有锁 | 保护临界区 |
| 读写锁 | 多读单写 | 读多写少 |
| 条件变量 | 等待某个条件成立再继续 | 生产者-消费者 |
| 信号量 | 控制并发访问数量 | 限流 |
| 自旋锁 | 忙等待，不切换上下文 | 临界区极短时 |
| 原子操作 | CPU 指令级原子性 | 简单计数器 |

**结合项目：** `rpc_manager.h` 的 `GrpcManagerImpl` 用 `std::mutex` + `std::lock_guard` 保护 `monitor_infos_`。gRPC 服务端是多线程回调的，多个客户端可能同时调 `SetMonitorInfo` 写数据，必须加锁保线程安全。

## 8. 死锁是什么？怎么避免？⭐必背

**答：** 死锁的四个必要条件（同时满足才死锁）：
1. **互斥**：资源一次只能被一个线程占用
2. **持有并等待**：持有资源的同时等待其他资源
3. **不可抢占**：资源不能被强制释放
4. **循环等待**：线程之间形成资源等待环

**避免方法：**
- 固定加锁顺序（所有线程按相同顺序获取锁）
- 使用 `std::lock()` 同时获取多个锁
- 使用 RAII 锁包装（`lock_guard`）防忘解锁
- 尽量缩减临界区大小
- 使用 `try_lock` + 回退重试

**结合项目：** 项目中每个 RPC 方法都只有一把锁，不存在死锁风险。`lock_guard` 保证即使方法中途异常也能释放锁，不会死锁。

---

## 9. 虚拟内存是什么？有什么好处？⭐必背

**答：** 虚拟内存是操作系统给每个进程提供的**独立地址空间**的抽象。进程看到的地址（虚拟地址）和真实物理地址之间通过**页表**映射。

**好处：**
1. **隔离性**：进程 A 不能访问进程 B 的内存，安全性
2. **简化编程**：每个进程都可以用从 0 开始的地址空间，不用关心物理内存布局
3. **内存超分配**：虚拟内存可以大于物理内存，不常用的页换出到磁盘（swap）
4. **共享**：不同进程的虚拟页可以映射到同一物理页（共享库、进程间共享内存）

**结合项目：** 监控项目读取 `/proc/meminfo` 采集内存数据，里面的 `SwapCached`、`Active`、`Inactive` 等字段就是内核管理虚拟内存的状态指标。

---

## 10. 内存管理：malloc/new 底层做了什么？⭐必背

**答：**
1. 小于 128KB：从堆的 **brk** 区域分配，移动 `program break` 指针
2. 大于 128KB：用 **mmap** 在堆和栈之间映射一块匿名内存
3. glibc 的 `ptmalloc` 维护空闲链表（fastbins、smallbins、largebins），分配时先查空闲链表
4. 如果空闲内存不够：触发 `brk()` 或 `mmap()` 系统调用向内核申请
5. 内核只分配虚拟地址，**真正物理内存分配发生在首次访问时（缺页中断）**

**结合项目：** 项目中 `new monitor::MemMonitor()` 在堆上分配对象，由 `shared_ptr` 管理生命周期。监控器对象很小（几个 float + string），不会触发 mmap。

---

## 11. 缺页中断（Page Fault）是什么？

**答：** 当进程访问一个虚拟地址，但页表中该页不存在或没有访问权限时，CPU 触发缺页异常。

**三种情况：**
1. **Minor Page Fault**：物理页存在但没映射到该进程（如共享库已被其他进程加载），只需更新页表 — 很快
2. **Major Page Fault**：数据在磁盘 swap 区或文件系统中，需要 I/O 读入 — 很慢
3. **Invalid Fault**：访问非法地址 → SIGSEGV 段错误崩溃

**结合项目：** `/proc/meminfo` 中的 `pgfault`、`pgmajfault` 就是缺页次数统计。

---

## 12. 堆和栈的区别？⭐必背

| 维度 | 栈 | 堆 |
|------|-----|-----|
| 分配方式 | 编译器自动（移动 SP） | 手动 `new/malloc` |
| 释放 | 函数返回自动释放 | 手动 `delete/free` |
| 大小 | 小（默认 8MB） | 大（受虚拟内存限制） |
| 速度 | 极快（一条 CPU 指令） | 慢（需要查找空闲块） |
| 碎片 | 无碎片 | 可能产生内存碎片 |
| 生命周期 | 作用域内 | 手动控制 |

**结合项目：** 项目中 `struct CpuStat cpu_stat;` 在栈上分配（函数内局部变量），函数返回后自动销毁。`new std::thread(...)` 在堆上分配，由 `unique_ptr` 管理。

---

## 13. 什么是上下文切换？开销在哪里？

**答：** CPU 从一个线程/进程切换到另一个时，需要保存当前执行状态（寄存器、PC、栈指针）并加载下一个的执行状态。

**开销来源：**
1. **直接开销**：保存/恢复寄存器、切换内核栈
2. **间接开销**：TLB（页表缓存）失效需要重新加载、CPU 缓存可能不命中（cold cache）
3. **进程切换额外开销**：切换页表（CR3 寄存器）、刷新 TLB

**结合项目：** 项目用 `std::this_thread::sleep_for(std::chrono::seconds(3))` 让采集线程主动休眠 3 秒，避免忙等待，不浪费 CPU 时间片，减少不必要的上下文切换。

---

## 14. 用户态和内核态的区别？系统调用的过程？

**答：** CPU 有不同的特权级别（x86 的 Ring0-Ring3）。用户态（Ring3）权限受限，不能执行特权指令（关中断、设置页表、直接 I/O）。内核态（Ring0）有完整权限。

**系统调用过程（以 `read()` 为例）：**
1. 用户程序调用 glibc 的 `read()` → 触发 `syscall` 指令
2. CPU 从 Ring3 切换到 Ring0，根据系统调用号跳到内核的 `sys_read()` 
3. 内核从用户空间拷贝参数，检查权限，执行实际 I/O
4. 返回结果，CPU 切回 Ring3

**结合项目：** `std::ifstream` 读 `/proc/stat` 时，底层触发 `open()` → `read()` → `close()` 系统调用。每次都要进出内核态。

---

## 15. 什么是缓存一致性？CPU 的三级缓存？

**答：** 现代 CPU 有 L1（每核私有，32-64KB，极快）、L2（每核私有，256-512KB）、L3（所有核共享，几 MB-几十 MB）三级缓存。多个 CPU 核心各自有缓存，当一个核心修改了内存，其他核心的缓存就"过期"了。**缓存一致性协议（MESI）** 保证所有核心看到的内存是最新的。

**结合项目：** 服务端的 `monitor_infos_[hostname] = *request` 写操作可能触发缓存行失效。`std::mutex` 的加锁/解锁涉及原子操作 + 内存屏障，保证锁的获取和释放对多核可见。

---

## 16. 大端序和小端序的区别？

**答：** 大端序（Big Endian）：高位字节存低地址。小端序（Little Endian）：低位字节存低地址。x86/x64 是小端序，网络字节序是大端序。

**结合项目：** Protocol Buffers 序列化时使用小端序（变长编码），反序列化时自动处理字节序。应用层一般不需要关心。

---

## 17. Linux 的内存布局是怎样的？

**答：** 32 位进程的虚拟地址空间（4GB）：
```
0x00000000 ────────────────────
            代码段 (.text)
            数据段 (.data, .bss)
            堆 (brk → 增长方向 ↓)
            ...
            ... (mmap 区域)
            ...
            栈 (← 增长方向 ↓)
            命令行参数/环境变量
0xFFFFFFFF ────────────────────
            内核空间 (1GB，32 位)
```

64 位进程地址空间巨大（48 位有效，256TB），布局类似但更稀疏。

# 第三部分：C++ 语言八股（5 分钟）

## 18. 虚函数是怎么实现的？虚函数表（vtable）？⭐必背

**答：** 编译器为每个有虚函数的类生成一张**虚函数表（vtable）**，表中存所有虚函数的地址。每个对象实例头部隐含一个**虚表指针（vptr）**指向所属类的 vtable。

**调用过程：**
```cpp
MonitorInter* p = new CpuStatMonitor();
p->UpdateOnce(&info);  
// → 通过 p 找到 vptr → vtable[0] → CpuStatMonitor::UpdateOnce()
```

**开销：** 每个对象多 8 字节（vptr），虚函数调用多一次间接寻址（vptr→vtable→函数）。

**结合项目：** `MonitorInter` 有两个虚函数 `UpdateOnce()` 和 `Stop()`，vtable 里有它们和 `~MonitorInter()` 的地址。`runner->UpdateOnce(&monitor_info)` 就是通过 vtable 多态调用。

---

## 19. 构造函数能不能是虚函数？析构函数为什么要虚？⭐必背

**答：** 构造函数**不能**是虚函数——因为构造对象时 vptr 还没初始化，不知道调哪个类的构造函数。析构函数**应该**是虚函数——当通过基类指针 `delete` 子类对象时，如果不是虚析构，只会调基类的析构函数，子类的成员不会正确释放。

```cpp
MonitorInter* p = new CpuStatMonitor();
delete p;  // 如果 ~MonitorInter() 不是 virtual，只调基类析构 → 内存泄漏
```

**结合项目：** `MonitorInter` 的析构函数声明为 `virtual ~MonitorInter() {}`，保证 `shared_ptr<MonitorInter>` 析构时正确调用子类析构函数。

---

## 20. 虚函数和纯虚函数的区别？

**答：**
- 虚函数：基类有默认实现，子类**可以**重写
- 纯虚函数（`= 0`）：基类无实现，子类**必须**重写，否则子类也是抽象类，不能实例化

**结合项目：** `MonitorInter::UpdateOnce() = 0` 是纯虚函数，强制每个监控器必须实现自己的采集逻辑。

---

## 21. 构造函数中能不能调虚函数？

**答：** 语法上可以，但**不按预期工作**。构造子类对象时，先执行基类构造函数，此时 vptr 还指向基类的 vtable，调虚函数会调基类的版本而不是子类的版本。同理，析构函数中调虚函数也不走多态（因为子类已经析构完了）。

---

## 22. RAII 是什么？项目中怎么用的？⭐必背

**答：** Resource Acquisition Is Initialization（资源获取即初始化）。核心：**将资源的生命周期绑定到对象的生命周期上**。构造时获取资源，析构时释放资源。

**项目的三个 RAII 实践：**

| 类 | 资源 | 获取（构造） | 释放（析构） |
|----|------|------------|------------|
| `ReadFile` | 文件句柄 | `ifs_.open(name)` | `ifs_.close()` |
| `std::lock_guard` | 互斥锁 | `mutex_.lock()` | `mutex_.unlock()` |
| `std::unique_ptr` | 堆内存 | `new T(...)` | `delete ptr` |

**好处：** 即使函数中途抛异常，栈展开时析构函数一定执行，永不泄漏。

---

## 23. 移动语义（move semantics）是什么？⭐必背

**答：** C++11 引入的机制，允许将资源的所有权从一个对象"转移"到另一个对象，而不是拷贝。

**左值 vs 右值：**
- 左值：有名字、能取地址的对象（变量）
- 右值：临时的、即将销毁的对象

**`std::move` 的本质：** 把左值强制转成右值引用，告诉编译器"这个对象我不需要了，你可以偷它的资源"。

```cpp
std::string a = "hello";
std::string b = std::move(a);  // a 的内部指针被"偷"给 b，a 变成空字符串
```

**结合项目：** `net_monitor.cpp` 中 `net_info_[name] = std::move(net_info)` 避免拷贝 `std::string name`，转移内部指针而非重新分配内存。

---

## 24. 左值引用和右值引用的区别？

**答：**
- `T&`（左值引用）：只能绑定到左值
- `T&&`（右值引用）：只能绑定到右值（临时对象）
- `const T&`（常量左值引用）：可以绑定到左值和右值（万能引用）

**结合项目：** `Utils::SteadyTimeSecond(const std::chrono::steady_clock::time_point& t1, ...)` 的参数用 `const &`，既能接受左值变量，也能接受右值临时对象。

---

## 25. 智能指针的底层原理？⭐必背

| 指针 | 所有权 | 实现 | 开销 |
|------|--------|------|------|
| `unique_ptr` | 独占 | 内部存裸指针，禁止拷贝，只允许移动 | 接近裸指针 |
| `shared_ptr` | 共享 | 内部存裸指针 + 指向控制块（引用计数）的指针 | 引用计数原子操作 |
| `weak_ptr` | 不拥有 | 配合 `shared_ptr`，不增加引用计数 | 需要 `lock()` 提升 |

**重要细节：**
- `shared_ptr` 的控制块和对象是分开分配的（make_shared 优化为合并分配）
- 引用计数用 `std::atomic`，线程安全的原子加减
- `weak_ptr` 解决循环引用：A 有 B 的 shared_ptr，B 有 A 的 shared_ptr → 引用计数永远不为 0 → 泄漏

**结合项目：**
- `runners_` 是 `vector<shared_ptr<MonitorInter>>`：因为 vector 需要拷贝存储，unique_ptr 不能拷贝
- `stub_ptr_` 是 `unique_ptr<Stub>`：gRPC Stub 独占所有权，不需要共享
- `thread_` 是 `unique_ptr<std::thread>`：线程对象独占

## 26. new/delete 和 malloc/free 的区别？

| 维度 | new/delete | malloc/free |
|------|-----------|-------------|
| 类型 | C++ 关键字/运算符 | C 库函数 |
| 调用构造函数 | ✅ 自动调用 | ❌ 不调用 |
| 返回类型 | 类型安全的指针 | `void*` 需要强转 |
| 失败行为 | 抛 `std::bad_alloc` | 返回 `NULL` |
| 大小 | 编译器自动算 | 需要手动传字节数 |
| 重载 | 可以重载 `operator new` | 不能重载 |
| 释放 | `delete` / `delete[]` | `free()` |

## 27. const 关键字的用法和好处？

**答：**
```cpp
const int x = 10;              // ① 常量，不可修改
int* const p = &x;             // ② 指针本身不可变
const int* p = &x;             // ③ 指针指向的内容不可变
void foo() const;              // ④ 成员函数不修改成员变量
const int& foo(const int& x);  // ⑤ const 引用参数，不可修改且接受临时对象
```

**好处：**
1. **编译期检查**：防止无意修改不该改的变量
2. **自文档化**：读代码的人知道这个值不会变
3. **优化可能**：编译器可以做常量折叠等优化
4. **接口约束**：`const &` 参数明确告诉调用者"我不会改你的数据"

**结合项目：** `RpcClient` 的 `SetMonitorInfo(const monitor::proto::MonitorInfo& monito_info)` 参数用 `const &`，不拷贝大对象，也明确不会修改输入。

## 28. 深拷贝和浅拷贝的区别？

**答：** 浅拷贝只拷贝对象本身（包括指针的值），指针指向的数据是共享的。深拷贝拷贝对象本身 + 指针指向的数据。

```cpp
struct Data {
    char* buf;
    // 浅拷贝：只拷贝 buf 指针值 → 两个对象指向同一块内存 → double free
    // 深拷贝：new 一块新内存，memcpy 过去 → 各管各的
};
```

**结合项目：** `monitor_infos_[hostname] = *request` 是 Protobuf 消息的赋值，Protobuf 实现了**深拷贝**。

---

## 29. 内存泄漏怎么排查？你遇到过的内存问题？

**答：**
- **Valgrind**：检测内存泄漏、越界访问、使用已释放内存
- **AddressSanitizer（ASan）**：编译时加 `-fsanitize=address`，运行时检测
- **智能指针**：用 `unique_ptr`/`shared_ptr` 替代裸指针从根本上防止泄漏

**结合项目：** 我项目中全部用智能指针（`unique_ptr`、`shared_ptr`）管理堆对象，`ReadFile` 用 RAII 管文件句柄，从根本上杜绝了泄漏风险。

## 30. STL 容器：vector 的扩容机制？

**答：** vector 在堆上分配连续内存。当 `size() == capacity()` 时再插入，触发扩容：
1. 分配一块更大的内存（通常是原来的 1.5 倍或 2 倍）
2. 把旧元素**移动或拷贝**到新内存
3. 释放旧内存

**为什么是 1.5 或 2 倍而不是每次 +1？** 均摊复杂度：N 次 push_back 总共拷贝 O(N) 次元素，平均 O(1)。如果每次 +1，会变成 O(N²)。

**结合项目：** `std::vector<std::string> cpu_load` 接收 `ReadLine` 的分割结果，大小不固定，取决于 `/proc` 文件每行的字段数。

## 31. map 和 unordered_map 的底层实现和选择？⭐必背

| 维度 | map | unordered_map |
|------|-----|---------------|
| 底层 | 红黑树 | 哈希表 |
| 查找 | O(log n) | 平均 O(1)，最坏 O(n) |
| 插入 | O(log n) | 平均 O(1) |
| 有序性 | 按键排序 | 无序 |
| 内存 | 较小 | 较大（需要桶数组） |
| 哈希冲突 | — | 链地址法 |

**结合项目：** 用 `unordered_map` 做 `cpu_stat_map_`（key=cpu 名），因为只需要快速查找不需要排序。哈希表的 O(1) 优于红黑树的 O(log n)。

## 32. 迭代器失效的情况有哪些？

**答：** 在遍历容器的同时修改容器，迭代器可能失效：
- `vector`：`push_back` 可能导致扩容，所有迭代器失效；`erase` 使被删元素及之后的所有迭代器失效
- `map/unordered_map`：`erase` 使被删元素的迭代器失效，不影响其他；`insert` 不失效
- `list`：`erase` 只失效被删元素的迭代器，`insert` 不失效

**安全做法：** `it = container.erase(it);` — erase 返回下一个有效迭代器。

**结合项目：** 项目中遍历 `monitor_infos_` 时没有修改容器结构（只读 `it->second`），所以迭代器安全。

## 33. C++ 编译链接过程？

**答：** 四步：
1. **预处理**：展开 `#include`、`#define`、条件编译 → `.i` 文件
2. **编译**：C++ → 汇编代码 → `.s` 文件
3. **汇编**：汇编代码 → 机器码 → `.o` 目标文件
4. **链接**：合并 `.o` 文件和库 → 可执行文件（ELF）

**静态链接 vs 动态链接：**
- 静态：库代码复制到可执行文件，体积大，独立运行
- 动态：运行时加载 `.so`，体积小，更新库不用重编译，但可能有版本兼容问题

**结合项目：** CMake 构建时，gRPC 和 Protobuf 一般是动态链接（`libgrpc++.so`），项目自己的代码编译成独立 `.o` 文件后链接。

---

## 34. extern "C" 的作用？

**答：** C++ 支持函数重载，编译时会做**名字修饰（name mangling）**——把参数类型编码到符号名里（如 `foo(int)` → `_Z3fooi`）。C 没有重载，不修饰名字。

`extern "C"` 告诉 C++ 编译器"这段代码按 C 的方式编译，不要做名字修饰"，这样 C 代码才能调用 C++ 的函数，C++ 也能调用 C 库。

**结合项目：** 如果要把监控库给 C 程序调用，头文件中需要 `extern "C"` 包裹接口函数。

---

## 35. static 关键字的三种用法？

**答：**
1. **static 局部变量**：生命周期 = 整个程序运行期间，只初始化一次
2. **static 全局变量/函数**：作用域限制在当前编译单元（.cpp 文件），外部不可见
3. **static 成员变量**：属于类而不是对象，所有实例共享；static 成员函数没有 `this` 指针

**结合项目：** 无静态局部变量，但 `constexpr float KBToGB = 1000 * 1000` 也是编译期常量，作用类似 static const。

# 第四部分：网络/gRPC/Protobuf 八股（3 分钟）

## 36. TCP 三次握手和四次挥手？ ⭐必背

**答：**

**三次握手（建立连接）：**
```
客户端                      服务端
SYN (seq=x)      ───────→
                 ←───────  SYN+ACK (seq=y, ack=x+1)
ACK (ack=y+1)    ───────→
连接建立！
```

**为什么是三次不是两次？** 防止已失效的连接请求到达服务端导致错误。如果是两次，服务端收到一个过期的 SYN 就会直接建立连接，浪费资源。

**四次挥手（断开连接）：**
```
主动方                      被动方
FIN              ───────→
                 ←───────  ACK
                 ←───────  FIN
ACK              ───────→
连接关闭！
```

**为什么是四次？** TCP 是全双工的，每个方向都要独立关闭。被动方收到 FIN 后可能还有数据要发，所以 ACK 和 FIN 分开发。

**结合项目：** gRPC 基于 HTTP/2（底层 TCP），服务端调用 `SetMonitorInfo` 时 TCP 连接已建立好，gRPC 做了连接复用，不需要每次 RPC 都三次握手。

---

## 37. TCP 和 UDP 的区别？

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠（确认+重传） | 不可靠 |
| 顺序 | 有序到达 | 可能乱序 |
| 流量控制 | 有（滑动窗口） | 无 |
| 拥塞控制 | 有 | 无 |
| 速度 | 较慢 | 快 |
| 适用 | 文件传输、HTTP、RPC | 视频直播、DNS、游戏 |

**结合项目：** gRPC 用 HTTP/2 over TCP，保证监控数据可靠传输。

---

## 38. HTTP/1.1 和 HTTP/2 的区别？

| 维度 | HTTP/1.1 | HTTP/2 |
|------|----------|--------|
| 格式 | 文本 | 二进制帧 |
| 连接 | 一个请求占一个连接（或 keep-alive 串行） | 多路复用（一个连接并行多个请求） |
| 头部压缩 | 无 | HPACK |
| 服务端推送 | 不支持 | 支持 |

**结合项目：** gRPC 基于 HTTP/2，多个 RPC 调用共享一个 TCP 连接，支持并发流，省去了 HTTP/1.1 的连接开销。

---

## 39. Protobuf 序列化原理？为什么比 JSON 快？⭐必背

**答：** Protobuf 使用**二进制编码**，核心是 **Varint（变长编码）** + **Tag-Length-Value**。

**Varint 编码：** 每个字节的最高位是"是否还有下一个字节"的标志位，低 7 位是数据。小数字只占 1 字节，大数字占多字节。大部分监控数据值较小，用 Protobuf 非常省空间。

**比 JSON 快的原因：**
1. 不解析文本（跳过词法分析、字符串→数字转换）
2. 编译时已知 schema，无需运行时反射
3. 二进制格式更紧凑，网络传输量小

**结合项目：** 单次采集 ~1.1KB 原始数据，用 Protobuf 压缩后约 200-300 字节。

---

## 40. gRPC 的四种服务模式？

**答：**
1. **一元 RPC**（Unary）：客户端发一个请求，服务端回一个响应。本项目用的就是这种
2. **服务端流式**：客户端发一个请求，服务端持续推送多条响应
3. **客户端流式**：客户端持续发送多个请求，服务端最后回一个响应
4. **双向流式**：双方可以独立地发送和接收

**结合项目：** `SetMonitorInfo` 和 `GetMonitorInfo` 都是一元 RPC。

---

## 41. RPC 和 HTTP REST 的区别？什么时候选哪个？

| 维度 | gRPC | REST |
|------|------|------|
| 协议 | HTTP/2 | HTTP/1.1 |
| 数据格式 | Protobuf（二进制） | JSON（文本） |
| 接口定义 | `.proto` 文件（强类型） | OpenAPI/Swagger（可选） |
| 性能 | 高 | 中等 |
| 浏览器支持 | 需要 grpc-web | 原生支持 |
| 调试 | 需要工具（grpcurl） | curl + 浏览器即可 |

**选择：** 服务间通信（微服务内部）→ gRPC；对外开放 API / 浏览器直接调用 → REST。

# 第五部分：项目深挖题（3 分钟）

## 42. 差分计算中，为什么首次采样不输出数据？⭐必背

**答：** 差分计算需要"上一次"的采样值做减法。首次采样时 `unordered_map` 里是空的，`find()` 找不到历史数据，所以跳过计算——只把当前采样值存下来，等第二次采集来了再做差分。这是一种**懒初始化**策略。

---

## 43. /proc/stat 里 guest 为什么不能和 user 重复加？

**答：** Linux 内核文档明确指出：`guest` 时间（虚拟化环境中运行虚拟 CPU 的时间）**已经包含在 `user` 时间里**。如果算总 CPU 时间时把 `user` 和 `guest` 都加上，就重算了。同理 `guest_nice` 包含在 `nice` 里。所以算总时间时要排除 `guest` 和 `guest_nice`。

---

## 44. 如果 `/proc/loadavg` 文件不存在或读取失败，会怎样？怎么改进？

**答：** 当前代码没有错误处理：
1. `ReadFile` 构造时 `ifstream` 打开失败 → 不抛异常，但 `ifs_` 处于失败状态
2. `ReadLine` 读失败 → 返回 `false`
3. `cpu_load[0]` 访问空 vector → **直接崩溃（UB）**

**改进方案：**
```cpp
ReadFile cpu_load_file("/proc/loadavg");
if (cpu_load_file.is_open()) {  // 检查文件是否成功打开
    std::vector<std::string> cpu_load;
    if (cpu_load_file.ReadLine(&cpu_load) && cpu_load.size() >= 3) {
        // 安全解析
    }
}
```

---

## 45. 如果多个监控客户端上报同一个主机名怎么办？

**答：** 服务端的 `monitor_infos_[hostname] = *request` 用等号直接覆盖，后来的覆盖先来的。也就是说同一个主机名只保留最新的那条记录。这是合理的设计——一个主机只需要最新的监控数据。

---

## 46. 项目中 `std::move` 用在哪里？为什么要用？

**答：** `net_monitor.cpp` 中：
```cpp
struct NetInfo old = std::move(iter->second);  // 从 map 移出旧数据
net_info_[name] = std::move(net_info);        // 移入新数据
```

`NetInfo` 结构体包含 `std::string name`，不用 `move` 的话赋值会触发字符串的深拷贝（分配内存 + 复制字符）。用了 `move` 后直接转移 `std::string` 内部的堆指针，零额外内存分配。

---

## 47. 从 `/proc` 读数据，是不是一次系统调用读一个字节？开销大吗？

**答：** `std::ifstream` 内部有缓冲区（通常是 8192 字节）。`std::getline` 从缓冲区取数据，只有缓冲区空了才触发一次 `read()` 系统调用。大部分 `/proc` 文件内容不超过几 KB，一次系统调用就能读完。所以性能开销很小。

---

## 48. 为什么要用 `std::make_shared` / 为什么你用 `new` + `shared_ptr`？

**答：** C++11 中 `std::make_shared` 是 C++11 引入的，会把对象和控制块（引用计数）合并在一次内存分配中，而 `shared_ptr<T>(new T(...))` 需要两次分配（一次 new 对象，一次 new 控制块）。`make_shared` 更高效。

但我项目用 `new` + `emplace_back(new ...)`，因为：
1. 写法更直观，新人容易理解
2. 监控器只在启动时创建一次，这点性能差异可以忽略

**注意：** `std::make_unique` 是 C++14 的，项目用 C++11，所以用 `unique_ptr<T>(new T(...))` 替代。

---

## 49. C++11 项目中不能用 `std::make_unique`，你是怎么做的？

**答：** 用 `std::unique_ptr<T>(new T(...))` 等价替代：
```cpp
// C++14:
thread_ = std::make_unique<std::thread>(...);
// C++11:
thread_ = std::unique_ptr<std::thread>(new std::thread(...));
```

C++17 的结构化绑定也不能用，改用迭代器：
```cpp
// C++17:
for (auto& [hostname, info] : monitor_infos_) { ... }
// C++11:
for (auto it = monitor_infos_.begin(); it != monitor_infos_.end(); ++it) {
    auto* host_info = response->add_hosts();
    *host_info = it->second;
}
```

---

## 50. gRPC 服务端使用非安全连接（Insecure），生产环境怎么改？

**答：** 替换 `InsecureServerCredentials()` 为 `SslServerCredentials()`，配置 TLS 证书。客户端那边也要换 `InsecureChannelCredentials()` 为 `SslCredentials()`。Protobuf 和 gRPC 的调用接口不变，只改连接凭证。

# 第六部分：场景设计题（2 分钟）

## 51. 如果让你加一个磁盘 I/O 监控，怎么做？⭐必背

**答：** 三步走：
1. **定义协议**：在 `proto/` 中新增 `disk_info.proto`，定义 `DiskInfo` 消息（设备名、读写速率、IOPS 等）
2. **实现监控器**：创建 `DiskMonitor` 类继承 `MonitorInter`，在 `UpdateOnce` 中读 `/proc/diskstats`，解析字段，做差分计算
3. **注册**：在 `main.cpp` 中加一行 `runners_.emplace_back(new DiskMonitor())`

不需要改主循环代码、不需要改 gRPC 通信层、不需要改其他监控器。这就是策略模式的好处——**对扩展开放，对修改封闭**。

---

## 52. 如果监控客户端从 1 个变成 100 个，服务端怎么扛住？

**答：**
1. **当前设计已经支持多主机**：`GrpcManagerImpl` 用 `unordered_map` 按主机名存数据
2. **用读写锁替代互斥锁**：`GetMonitorInfo`（读操作）远多于 `SetMonitorInfo`（写操作），读写锁能让多个读并发
3. **限流**：限制每个客户端的上报频率
4. **服务端横向扩展**：多个服务端实例 + 负载均衡
5. **数据分层**：服务端只做转发，数据存到 Redis/InfluxDB

---

## 53. 如果监控需要 1 秒采集一次，目前的设计有什么问题？

**答：** 目前的每 3 秒 `sleep_for(3s)` 只是控制采集频率。改成 1 秒后：
1. gRPC 同步调用如果返回慢（>1 秒），采集就会错位
2. 数据量变大 3 倍，对服务端缓存压力增加
3. 需要确认 `/proc` 文件的更新频率是否支持 1 秒精度（大部分可以）

更好的做法是用定时器或 `sleep_until` 校正时间漂移。

---

## 54. 如果要支持 Windows 平台，需要怎么改？

**答：** 核心改动在数据采集层——Windows 没有 `/proc` 文件系统。需要：
1. 用 Windows API 替代 `/proc` 读取：
   - CPU 使用率 → `GetSystemTimes()`
   - 内存 → `GlobalMemoryStatusEx()`
   - 网络 → `GetIfTable()` / `GetIfEntry2()`
2. 监控接口保持 `MonitorInter` 不变，写 Windows 版本的子类
3. CMake 中区分平台编译不同源文件
4. gRPC 和 Protobuf 跨平台，不需要改
